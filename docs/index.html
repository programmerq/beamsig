The problem

            
A swarm of agents commits code. Which one wrote this?

            

              Agents run in ephemeral sandboxes and commit as the human who
              launched them. Standard tooling cannot tell you which sandbox
              produced an artifact — it was never designed to. Here is the same
              signed commit, read three ways.
            

          


          

            

              
What git reports

              
Good "git" signature for root

              

                Git can tell you a signature is valid, but not which agent did
                the work. There is no identity here to tie the commit back to
                anything.
              

            


            

              
What GitHub reports

              
Unverified
reason: unknown_signature_type

              

                GitHub has the same blind spot. Neither tool gives you
                provenance you can tie back to the agent that produced the
                work.
              

            


            

              
What the certificate says

              
beam-1786bcd6-04b9-4b9e-ad87-0c13071df7e9
cluster  jeff.beams.sh
owner    owner@example.com

              

                A beam-signed commit names the sandbox that produced it and the
                Teleport session that launched the agent. That is provenance you
                can verify after the fact and trace back through the cluster.

How it works

            
Three facts make a signature self-contained.

          


          

            

              
The beam signs with its certificate

              

                A beam's key lives behind Teleport's hardware key agent and
                never leaves it. Signing with the certificate rather
                than a bare key makes the SSHSIG blob embed the entire
                certificate, so the evidence travels with the signature.
              

            


            

              
The certificate names the beam

              

                The beam identity lives in certificate extensions, not in the
                parts tooling usually shows:
                bot-name@goteleport.com = beam-<uuid>, plus
                the instance and delegation session that produced it.
              

            


            

              
Anyone verifies it offline

              

                Checking a signature needs the signature, the payload, and the
                ~200-byte Teleport user CA — pinned by value. No cluster, no
                network, no beam. It still verifies years later, against a
                long-expired certificate.
              

            

          

        

      


      
      

        

          

            
Read this before you trust it

            
What a passing check does not mean.

            
A verified beam signature is a narrow, precise claim.

          


          

            

              
The signer is a sandbox, never a person

              

                The certificate's Key ID is the owner — a human — because
                the beam impersonates them. Anything running inside the beam can
                sign as the beam: the signing agent has no client auth, no PIN
                and no touch.
              

              
✕ signed by owner@example.com

              

                ✓ signed by beam 1786bcd6… · on behalf of owner@example.com
                (impersonated, did not review this)
              

            


            

              
The friendly alias proves nothing

              

                Names like clever-nebula appear in no certificate,
                extension or OID. The mapping from UUID to alias is live cluster
                state that dies with the beam, and aliases may be reused later.
              

              

                Only the UUID is attested, and that is the identifier worth
                having: it is what lets you verify a commit later and trace it
                back to the Teleport session that launched the agent.
              

            


            

              
The timestamp is a window the signer chose

              

                A beam's certificate rotates every ~20 minutes, but its key
                never does. A signer can embed an older certificate it still
                holds and so choose the window you see. Backdating within the
                beam's lifetime is possible; forward-dating is not.
              

            

          

        

      


      
      

        

          

            
Quickstart

            
Sign every commit in your beam.

            

              Run this inside a beam — signing needs the hardware key agent, which
              only exists there. Verification, by contrast, runs anywhere.
            

          


          

            

              

                inside a beam
                
              

              
$ git clone https://github.com/programmerq/beamsig.git
$ cd beamsig

# venv, gRPC stubs, and pin this cluster's CA
$ ./bin/setup.sh

# beam-wide git signing + a beam-aware git log
$ ./bin/install-global.sh

# every commit in this beam is now signed by the beam
$ git commit -m "fix the parser"
$ git log --format='%GS'
beam-1786bcd6-04b9-4b9e-ad87-0c13071df7e9
